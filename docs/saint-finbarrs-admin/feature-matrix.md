# Feature matrix — every live feature, and what this project did with it

Generated by `tools/audit/build-feature-matrix.py` from `admin-registry.ts`,
`nav.ts` and `admin-panels.ts`, so it cannot drift from the code.

## Status vocabulary

| Status | Meaning |
|---|---|
| **Implemented** | Read, write and permissions all present. The only variation between modules is the column set. |
| **Partial** | A real part is missing and is named in the note. |
| **Divergence** | Present and working, but deliberately different from the live app, with the reason. |
| **Reproduces a live failure** | The live page is broken; this one is broken the same way rather than papered over. |
| **LAEC panel** | Pre-existing this-project markup, untouched by this audit, carried as a regression check. |

## Totals

- Registry modules: **66**, plus the summary dashboard: **67** panels.

- Rendered by a bespoke component: **54**, drawn by **18** components.
- Rail entries for SUPER_ADMIN: **75** (68 modules + 7 LAEC panels).
- Permission codes in the vocabulary: **180**.

- Modules declaring a `customPanel` that no component answers for: `fee-payments`, `wallets`. These render through `AdminResourcePanel.vue`, which is correct for both — the label names the module, not a component.

## Deliberate divergences, partials and reproduced failures

**`academic-settings` — Reproduces the live read failure as an error card.** The live page's own read fails and shows "Couldn't load academic settings". Reproducing it is the faithful behaviour; inventing a grading-scale form would document a feature that does not exist there. The form that DOES exist is `/results/grading`, reproduced as `grading`.

**`branding` — Reproduces the live read failure as an error card.** Same reasoning: "Couldn't load branding settings" is what the live page shows.

**`cart` — Implemented.** Cart lines with quantity and removal, the online/bursary choice, and PLACE_STORE_ORDER creating an order the bursary queue then gains. See workflows.md, W20.

**`leave-approvals` — Divergence.** Approve/Reject are gated on `leave.approve`. The deployed `LeaveDetailPage` renders them for any PENDING row with no permission check at all. Gating them here would be the opposite of the live bug, and shipping an ungated control the rail already says this session does not hold is worse. See roles-and-permissions.md.

**`notification-settings` — Reproduces the live read failure as an error card.** Same reasoning: "Couldn't load notification settings".

**`orders` — Implemented.** Order history from the mock, including orders placed through checkout.

**`roles` — Scope decision.** The 33 school roles are seed data, editable and readable, but they do not gate the console. A session in this project carries one LAEC claim, not one of 33 school roles; the two axes are not interchangeable. The console gate is `leave.approve`-style codes, not role names.

**`staff-attendance-report` — Divergence.** Same: the trend block is per-week tallies, for the same reason.

**`store` — Implemented.** Catalogue, search, category filter and the cart badge. Checkout is a real transaction — see workflows.md, W20.

**`student-attendance-report` — Divergence.** "Daily Attendance Trend" is rendered as per-week tallies rather than a chart, because the mock's attendance data has a week dimension and no day series. A chart over weeks would have to invent the days it plots.

## Live routes deliberately not implemented

The audit reached 131 live routes. The ones with no panel here are named in `route-inventory.md` (every row whose Panel column is `—`). They fall into four groups, and none is an oversight:

1. **Teacher-portal surfaces** — `/lesson-planning*`, `/weekly-report*`, `/teacher/*`, `/staff-portal/*`. These already exist in this project on `/teacher/`, built and verified in a separate audit (`docs/teacher-portal/`). Rebuilding them inside `/admin/` would duplicate a console.
2. **Communication** — `/communication/messages`, `/communication/logs`, `/communication/templates*`. The notice board and events calendar already exist here on `/notices/` and `/calendar/`; the rail's School group routes to them. Messaging is a per-conversation surface outside an admin console's remit. `logs` and `templates` render *Under construction* placeholders on the live deployment, so there is nothing to reproduce.
3. **Disciplinary and Counselling** — now implemented, on eight panels and two shared components. What is *not* reproduced is stated rather than hidden: the live incident catalogue holds 33 offences and this seeds the 9 that were captured verbatim before the crawl truncated (the rest are server-side data, absent from the deployed frontend source too, and an invented rule in a rule book is worse than a missing one — `parity-report.md` §12); the student picker is a fixed list because the mock has no directory to search; and severity is filtered client-side because the teacher-side read takes no severity argument.
4. **The parent-facing surface** — `/parent/*`. Three of the seven are 404s on the live deployment (`/parent/counselling`, `/parent/disciplinary`, `/parent/payments`, `/parent/store`); the rest are a parent's own view of their child, which belongs to a parent console this project does not have.

`/forgot-password`, `/profile` and `/unauthorized` already exist on other routes here.
